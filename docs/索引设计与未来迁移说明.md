# 索引设计与未来迁移说明

本文档说明 v4 数据库设计为什么不仅适用于微信云开发，也适合未来迁移到独立 App / Web 后端。

注意：本文档是 **v4 的未来迁移与扩展说明**，不是当前 MVP 建库清单。当前必须创建哪些集合，以 [数据库与语料系统设计-v4执行版.md](数据库与语料系统设计-v4执行版.md) 为准。

## 1. 核心判断

当前设计不是微信小程序专属模型，而是通用数据模型：

```text
实体表：
  words
  wordbooks
  content_topics
  content_lines

当前关系表：
  wordbook_words
  content_line_words

未来可扩展关系表：
  word_relations

用户状态表：
  users
  user_word_progress
  user_book_progress
```

迁移到 PostgreSQL / Supabase / MySQL / MongoDB 时，v4 的核心结构不需要推翻。`word_relations` 是未来增强同义词、易错词、运营推荐时再加的扩展表，不是 MVP 必建集合。

微信云开发里叫“集合”：

```text
words
wordbook_words
user_word_progress
content_line_words
```

独立后端里叫“表”：

```sql
words
wordbook_words
user_word_progress
content_line_words
```

查询路径和索引规律基本一致。

## 2. 为什么不要把归属塞进 words

v4 已经删除 `wordbook_words.tags`，也不建议用 `words.tags = ["ielts", "toefl"]` 承载主要业务关系。

原因：

- 一个词可能属于多本词书，每本词书里的顺序、重点程度、章节都不同。
- 一个词可能不是任何词书的正式成员，但它是某个 IELTS 主词的同义词或易错词。
- 一个词可能被 Valorant / 美剧语料命中，但这不代表它属于某本词书。
- 用户进度是对单词实体的掌握，不应该绑定到某个 tag 字符串上。

正确方式：

```text
词属于词书：
  wordbook_words

词和词之间有关联：
  MVP 阶段先放在 words.senses[] 的词典字段里
  未来可扩展 word_relations

词被语料句子命中：
  content_line_words

用户学过某个词：
  user_word_progress
```

`words` 只做单词实体主表。

## 3. 主要查询路径

### 3.1 学 IELTS

查询入口不是 `words`，而是：

```text
wordbook_words where bookId = "ielts" order by order
```

索引：

```text
wordbook_words:
  bookId + order
  bookId + wordId unique
```

SQL 迁移后：

```sql
CREATE INDEX idx_wordbook_words_book_order
ON wordbook_words (book_id, "order");

CREATE UNIQUE INDEX idx_wordbook_words_book_word
ON wordbook_words (book_id, word_id);
```

### 3.2 查一个词属于哪些词书

查询：

```text
wordbook_words where wordId = "word_accurate"
```

索引：

```text
wordbook_words:
  wordId
```

SQL：

```sql
CREATE INDEX idx_wordbook_words_word
ON wordbook_words (word_id);
```

### 3.3 用户查词 / 搜索

MVP 阶段只做精确查询和前缀搜索：

```text
words.normalized exact
words.normalized prefix limit 20
```

索引：

```text
words:
  normalized unique
```

SQL：

```sql
CREATE UNIQUE INDEX idx_words_normalized
ON words (normalized);
```

未来迁到 PostgreSQL 后可以升级：

```sql
CREATE INDEX idx_words_normalized_trgm
ON words USING gin (normalized gin_trgm_ops);
```

这样可以支持更好的模糊搜索，比如：

```text
accurte -> accurate
```

说明：

- v4 当前没有 `words.searchKey` 字段。
- 如果未来要加 `searchKey`，需要先在主设计文档里补 schema，明确它是 `string` 还是 `string[]`，以及是否包含词形变化、别名、拼写纠错键。
- PostgreSQL `gin_trgm_ops` 适合英文模糊搜索；中文搜索不要依赖 trigram，未来应考虑 ES / Meilisearch / pg_jieba 等方案。

### 3.4 查同义词 / 易错词 / 反义词（未来扩展）

v4 MVP 里，CET4 已有的同义词、反义词、同义词例句先放在：

```text
words.senses[].synonyms
words.senses[].antonyms
words.senses[].gamingLink
```

这些属于“词典固化内容”，随词条导入，默认只读。

未来如果要做运营可写的易错词、跨词推荐、用户个性化关系，再新增：

```text
word_relations
```

分工：

```text
senses[].synonyms:
  词典层，只读，带 nuance / example。

word_relations:
  运营层 / 推荐层，可写，用于 confused_with、related、derivative、manual recommendation。
```

查询：

```text
word_relations where fromWordId = "word_accurate"
```

索引：

```text
word_relations:
  fromWordId + relationType
  toWordId
```

SQL：

```sql
CREATE INDEX idx_word_relations_from_type
ON word_relations (from_word_id, relation_type);

CREATE INDEX idx_word_relations_to
ON word_relations (to_word_id);
```

未来 `word_relations` schema 建议：

```js
{
  _id: "rel_word_accurate_word_precise_synonym",
  fromWordId: "word_accurate",
  toWordId: "word_precise",
  relationType: "synonym",
  sourceType: "manual",
  note: "",
  createdAt: 1779700000000,
  updatedAt: 1779700000000
}
```

关系方向规则：

```text
单向存储。
A -> B 与 B -> A 是两条独立记录。
查 X 主动关联的词：where fromWordId = X
查 X 被哪些词关联：where toWordId = X
```

例如 `synonym` 也不强制自动双向展开。是否生成反向记录由导入脚本或运营后台决定。

触发新增 `word_relations` 的条件：

```text
1. 需要运营后台维护易错词 / 相关词。
2. 需要在多个词书之间复用人工关系。
3. 需要把“词典同义词”和“学习推荐关系”分开管理。
```

### 3.5 查主题例句

比如用户在单词详情页看 Valorant 例句：

```text
content_line_words where wordId = "word_accurate" and topicId = "valorant"
```

索引：

```text
content_line_words:
  wordId + topicId
  lineId
```

SQL：

```sql
CREATE INDEX idx_content_line_words_word_topic
ON content_line_words (word_id, topic_id);

CREATE INDEX idx_content_line_words_line
ON content_line_words (line_id);
```

### 3.6 查用户进度

单词掌握状态：

```text
user_word_progress where userId = X and wordId = Y
```

到期复习：

```text
user_word_progress where userId = X and nextReviewAt <= now
```

索引：

```text
user_word_progress:
  userId + wordId unique
  userId + nextReviewAt
  userId + status
```

SQL：

```sql
CREATE UNIQUE INDEX idx_user_word_progress_user_word
ON user_word_progress (user_id, word_id);

CREATE INDEX idx_user_word_progress_due
ON user_word_progress (user_id, next_review_at);

CREATE INDEX idx_user_word_progress_status
ON user_word_progress (user_id, status);
```

## 4. 不属于任何词书的词怎么被找到

有些词不是 IELTS 主词，但仍然应该进入 `words`。

例子：

```text
accurate 是 IELTS 主词
precise 是 accurate 的同义词
precise 不一定属于 IELTS
```

当前 v4 MVP 结构：

```text
words:
  word_precise

words.senses[].synonyms:
  accurate 的词典同义词里出现 precise
```

未来如果 precise 需要成为可运营、可推荐、可单独追踪的关系，再写入 `word_relations`。

用户可以通过这些路径找到它：

```text
1. 在 accurate 详情页的 senses[].synonyms 里看到 precise
2. 主动搜索 precise
3. 某条主题语料命中 precise
4. 未来 TOEFL 导入后，precise 被加入 wordbook_words
```

所以“不属于词书”不代表“不可访问”。它只是不会出现在某本词书的学习清单里。

## 5. 迁移到独立 App / Web 的变化

### 5.1 数据结构变化

微信云开发：

```text
collection
document
cloud function
```

独立后端：

```text
table
row
REST / GraphQL / RPC API
```

但核心结构不变：

```text
words
wordbooks
wordbook_words
content_topics
content_lines
content_line_words
user_word_progress
user_book_progress
```

未来可能增加：

```text
word_relations
```

本文档不再建议单独建立 `word_examples`。v4 当前已有：

```text
words.senses[].synonyms[].exampleEn / exampleZh
content_lines + content_line_words
```

如果未来出现“用户自定义例句”或“运营人工例句库”，再单独设计 `word_examples`。

### 5.2 字段命名变化

微信阶段：

```text
wordId
bookId
userId
topicId
nextReviewAt
```

SQL 阶段：

```text
word_id
book_id
user_id
topic_id
next_review_at
```

这是机械迁移，不影响模型。

### 5.3 身份体系变化

微信小程序阶段：

```text
openid
```

独立 App / Web 阶段：

```text
account_id
email / phone / apple / wechat identity
```

建议迁移目标：

```sql
accounts (
  id uuid primary key
)

account_identities (
  account_id uuid,
  provider text,
  provider_user_id text
)
```

微信 `openid` 会变成：

```text
provider = wechat
provider_user_id = openid
```

当前文档里的 `accountId` 就是为了给未来迁移留位置。

微信阶段的 `accountId` 是字符串，默认等于 `openid`。迁移到 SQL 时建议：

```text
1. 为每个现有 accountId 生成新的 uuid，写入 accounts.id。
2. 旧 accountId / openid 不继续当主键。
3. 旧 openid 写入 account_identities.provider_user_id。
```

迁移细节：

```text
微信阶段：
  user_word_progress._id = "openid:wordId"

SQL 阶段推荐：
  不依赖字符串 _id。
  使用 (account_id, word_id) 作为唯一约束或复合主键。
```

也就是说，迁移到 SQL 后不要继续从 `_id` 字符串里拆 user 和 word，应该显式使用列：

```sql
CREATE UNIQUE INDEX idx_user_word_progress_account_word
ON user_word_progress (account_id, word_id);
```

`openid` 迁移到 `account_identities` 后作为历史身份保存：

```text
一个 account 可以绑定多个 identity。
旧 openid 不删除，作为 provider=wechat 的一条 identity。
如果未来用户更换微信身份，需要通过登录绑定流程合并到同一个 account。
```

## 6. 独立后端能增强的能力

微信云数据库限制较多：

```text
join 弱
全文搜索弱
复杂聚合弱
事务能力有限
分页和批量写入不舒服
```

迁到 PostgreSQL / Supabase 后，可以增强：

```text
SQL JOIN
事务
批量 upsert
全文搜索
trigram 模糊搜索
复杂统计
```

例如单词详情可以一次性查：

```sql
SELECT *
FROM words w
WHERE w.id = 'word_accurate';
```

如果未来增加 `word_relations`，再 join：

```sql
SELECT *
FROM word_relations r
WHERE r.from_word_id = 'word_accurate';
```

主题例句可以用：

```sql
SELECT l.*
FROM content_line_words lw
JOIN content_lines l ON l.id = lw.line_id
WHERE lw.word_id = 'word_accurate'
  AND lw.topic_id = 'valorant';
```

## 7. JSON 字段怎么迁

当前有些字段适合先作为对象保存：

```text
phonetic
audio
senses
speaker
scene
source
cover
```

迁到 PostgreSQL 后可以先用 `jsonb`：

```sql
phonetic jsonb
audio jsonb
senses jsonb
speaker jsonb
scene jsonb
```

等某些字段变成高频查询条件，再拆成独立列或独立表。

例如：

```text
senses 暂时 jsonb
speaker.name 如果经常筛选，就独立成 speaker_name
scene.section 如果经常筛选，就独立成 section
```

## 8. 未来可预埋字段

这些字段不是 v4 MVP 必须项，但未来做独立 App / Web 时可以考虑：

```text
words.language:
  默认 "en"，未来支持日语、韩语等多语言时有用。

words.embedding:
  可用 pgvector / 向量数据库保存语义向量，支持 AI 语义检索。

words.searchKey:
  如需添加，必须先定义 schema。建议明确是 string 还是 string[]，是否包含 aliases、词形变化、拼写纠错键。
```

这些字段不应在当前 v4 建库阶段强行加入，避免 MVP 复杂化。

## 9. 同形异义词拆分时机

v4 MVP 一词一记录，`lead / bank / well` 这类同形异义词暂不拆。

触发拆分的条件：

```text
1. 需要按义项做 SRS，例如 bank#river 与 bank#finance 进度分开。
2. 用户反馈同一拼写的多个义项学习状态混乱。
3. 例句和语料需要精确挂到某个义项，而不是整个 word。
```

到那时再引入：

```text
word_senses
sense_examples
user_sense_progress
```

不要在 MVP 提前拆，成本高，收益暂时不明显。

## 10. 结论

当前索引规律适合未来独立 App / Web。

关键不是微信云开发，而是这套原则：

```text
words 是节点表。
wordbook_words 表达词书归属。
words.senses 表达词典固化释义、同义词、反义词、词典例句。
未来 word_relations 表达运营可写的单词关系。
content_line_words 表达语料命中。
user_word_progress 表达用户掌握状态。
```

只要坚持：

```text
不要把所有关系塞进 words.tags
不要把用户进度绑死在某本词书里
不要把主题语料混进词书
```

未来从微信云开发迁到 Supabase / PostgreSQL / 独立 API 时，就是：

```text
集合 -> 表
复合索引 -> SQL index
云函数手动 join -> SQL join
openid -> account identity
```

这套设计不会浪费，反而是在给后续多端产品留路。
