# 学习题型系统扩展设计方案

本文档用于设计 `learn` 页后续怎么从单一题型扩展到多题型系统。

当前学习页只支持一种题型：

```text
看英文单词 -> 选择中文释义
```

后续希望支持：

```text
看中文选英文
看英文解释选单词
单词拼写
听音辨词
例句填空
近义词 / 易混淆辨析题
AI 生成练习题
```

核心目标是：题型可以不断增加，但学习进度、SRS、答题统计、连击音效、错题重试这些机制不要重写。

## 1. 当前问题

现在 `learn` 页的数据流大概是：

```text
currentWord
  当前学习单词

currentChoices
  当前词的 4 个中文释义选项

word-card
  固定展示英文单词、音标、中文释义选项
```

当前出题逻辑：

```text
buildChoices(currentWord, pool)
  1. 当前词中文释义作为正确答案
  2. 从其他词里抽 3 个中文释义作为干扰项
  3. shuffle 后给 word-card
```

这个结构的限制是：

```text
word-card 只适合选择题
选择题只适合“英文 -> 中文”
题目本身没有独立结构
学习页无法区分这次练的是识别、回忆、拼写还是辨析
AI 生成题不好接入
```

所以需要把“单词”和“题目”拆开。

## 2. 核心设计

新增一个统一的 `question` 对象。

学习页不再直接把 `word + choices` 传给组件，而是传：

```text
currentQuestion
```

基本结构：

```js
{
  id: "q_word_purpose_word_to_zh_1780000000000",
  type: "word_to_zh",
  wordId: "word_purpose",
  word: "purpose",
  normalized: "purpose",
  senseId: "purpose_n_01",
  prompt: {},
  choices: [],
  answer: {},
  meta: {}
}
```

字段含义：

```text
id:
  本次题目的本地唯一 ID，方便调试和记录

type:
  题型，比如 word_to_zh / zh_to_word / spelling

wordId:
  这道题最终归属到哪个单词，用于 SRS 和用户进度

senseId:
  如果题目针对某个义项，写具体 senseId；不确定时可以为空

prompt:
  题干数据，不同题型结构不同

choices:
  选择题选项。非选择题可以为空

answer:
  标准答案结构。不同题型结构不同

meta:
  难度、来源、是否 AI 生成、是否复习题等补充信息
```

## 3. Question Schema 权威定义

后续出题器、AI 题校验、`question-card` 组件、单元测试都以这一节为准。第 4 节的示例只用于说明，不作为 schema 的权威来源。

### 3.1 顶层字段

```js
{
  id: "q_word_purpose_word_to_zh_001",
  type: "word_to_zh",
  wordId: "word_purpose",
  word: "purpose",
  normalized: "purpose",
  senseId: "purpose_n_01",
  prompt: {},
  choices: [],
  answer: {},
  meta: {}
}
```

必填字段：

```text
id
type
wordId
word
normalized
prompt
answer
meta
```

可选字段：

```text
senseId
choices
```

规则：

```text
wordId:
  题目最终归属到哪个单词。SRS 始终按 wordId 更新

senseId:
  题目针对哪个义项。没有明确义项时可以为空字符串

choices:
  选择题必须有 choices；非选择题可以为空数组
```

### 3.2 choices 统一结构

`choices[].value` 永远使用 `wordId`。如果选项指向的是具体义项，再额外写 `senseId`。

```js
{
  id: "a",
  text: "目的；用途",
  value: "word_purpose",
  wordId: "word_purpose",
  senseId: "purpose_n_01",
  correct: true
}
```

这样学习页接到答案时不需要根据题型猜 `value` 是 `wordId` 还是 `senseId`。

字段说明：

```text
id:
  选项本题内唯一 ID

text:
  前端展示文本

value:
  永远等于 wordId

wordId:
  选项对应的单词

senseId:
  选项对应的义项，可为空

correct:
  是否正确
```

### 3.3 answer 结构

选择题：

```js
{
  type: "choice",
  value: "word_purpose",
  wordId: "word_purpose",
  senseId: "purpose_n_01",
  text: "目的；用途"
}
```

拼写题：

```js
{
  type: "text",
  value: "purpose",
  normalized: "purpose",
  acceptable: ["purpose"]
}
```

拼写判定规则：

```text
1. 用户输入和标准答案都 trim()
2. 转小写
3. 合并连续空格
4. 去掉首尾标点
5. 与 answer.acceptable[] 中任一 normalized 值相等则正确
```

英美拼写、常见变体、短语空格差异都放进 `acceptable`。

示例：

```js
{
  type: "text",
  value: "color",
  normalized: "color",
  acceptable: ["color", "colour"]
}
```

### 3.4 prompt 结构

不同题型的 `prompt` 结构不同，但必须包含 `lang`。

```text
lang:
  zh   中文题干
  en   英文题干
  mixed 中英混合
```

各题型 prompt：

```js
// word_to_zh
{
  lang: "en",
  word: "purpose",
  phonetic: "/ˈpɜːpəs/",
  showAudio: true
}
```

```js
// zh_to_word
{
  lang: "zh",
  text: "目的；用途",
  hint: "选择对应的英文单词"
}
```

```js
// spelling
{
  lang: "zh",
  translation: "目的；用途",
  phonetic: "/ˈpɜːpəs/",
  letters: ["p", null, "r", "p", null, "s", "e"]
}
```

`letters` 中的 `null` 表示需要用户填写的位置。第一版如果只做普通输入框，也可以先不渲染 `letters`，但出题器仍然按结构化字段生成。

```js
// definition_to_word
{
  lang: "en",
  definitionEn: "the reason why something exists, is done, or is used"
}
```

```js
// relation_compare
{
  lang: "zh",
  text: "强调“为什么做这件事”时，哪个词更合适？",
  relationId: "rel_word_purpose_purpose_n_01_word_goal_goal_n_01_near_synonym"
}
```

### 3.5 meta 结构

不要把“谁生成的”和“数据从哪来”混在一个字段里。

统一结构：

```js
{
  generator: "rule",
  dataSource: "word",
  difficulty: 1,
  reviewIntent: "recognition"
}
```

字段枚举：

```text
generator:
  rule      本地规则生成
  ai        AI 生成
  manual    人工维护

dataSource:
  word        words 基础单词数据
  definition  英文释义
  relation    word_relations / word_relation_groups
  corpus      content_lines / content_line_words
  audio       单词发音或语料音频

reviewIntent:
  recognition     识别
  recall          回忆
  spelling        拼写
  discrimination  辨析
```

### 3.6 type 对照表

```text
type                 prompt.lang  answer.type  choices[].value  主要训练能力

word_to_zh           en           choice       wordId           英文识别
zh_to_word           zh           choice       wordId           中文到英文回忆
definition_to_word   en           choice       wordId           英文释义理解
audio_to_word        en/mixed     choice       wordId           听音辨词
spelling             zh/mixed     text         无               拼写回忆
sentence_blank       en/mixed     choice/text  wordId 或无       语境使用
relation_compare     zh/en        choice       wordId           近义词/易混淆辨析
```

## 4. 题型枚举

第一阶段建议支持 3 个题型：

```text
word_to_zh
  看英文单词，选择中文释义

zh_to_word
  看中文释义，选择英文单词

spelling
  看中文释义 / 音标，拼写英文单词
```

第二阶段再支持：

```text
definition_to_word
  看英文解释，选择英文单词

audio_to_word
  听发音，选择英文单词

sentence_blank
  例句挖空，选择或输入单词

relation_compare
  近义词 / 易混淆词辨析题
```

第三阶段支持 AI 生成题：

```text
ai_example_choice
  AI 生成场景选择题

ai_relation_quiz
  AI 根据词群关系生成辨析题
```

## 6. 前端组件拆分

当前 `word-card` 同时承担：

```text
展示单词
展示选项
判断答案
触发 choose
```

后续建议拆成：

```text
question-card
  根据 question.type 渲染题干

choice-options
  渲染选择题选项

spelling-input
  渲染拼写输入题
```

第一阶段也可以不拆太碎，先把 `word-card` 升级成 `question-card`：

```text
properties:
  question
  answered

events:
  answer
  play
  detail
```

组件只负责 UI 和本地判断，不负责更新 SRS。

事件结构：

```js
{
  questionId: "q_word_purpose_word_to_zh_001",
  wordId: "word_purpose",
  senseId: "purpose_n_01",
  type: "word_to_zh",
  result: "known",
  correct: true,
  value: "word_purpose",
  answerText: "目的；用途"
}
```

学习页接到事件后统一处理：

```text
更新 SRS
更新本地进度
同步云端
播放答题音效
处理错题重试
切下一题
```

## 7. 出题器设计

新增一个本地出题模块：

```text
miniprogram/utils/question-builder.js
```

对外暴露：

```js
buildQuestion(word, distractorPool, options)
```

输入：

```js
{
  word,
  distractorPool,
  mode: "daily" | "review",
  preferredTypes: ["word_to_zh", "zh_to_word", "spelling"],
  progress,
  retryPolicy: "same_question" | "easier_question"
}
```

输出：

```js
question
```

`distractorPool` 是干扰项池，不一定等于当前 session 的学习词。它可以来自当前词书全量词、当前章节、语义近词、词群关系词，具体由题型决定。

示例：

```text
word_to_zh:
  优先用同词书、相近词性、释义长度相近的词作为干扰项

definition_to_word:
  优先用同义词、近义词、易混淆词作为干扰项

relation_compare:
  直接用 word_relations 里的关系词作为选项
```

内部可以按规则选择题型：

```text
新词:
  优先 word_to_zh

已经答对过 1 次:
  增加 zh_to_word

已经答对过 2 次:
  增加 spelling

复习模式:
  混合 word_to_zh / zh_to_word / spelling

困难词:
  降低难度，优先 word_to_zh
```

这样题型难度会随着用户掌握程度逐步增加。

## 8. 进度和 SRS 怎么兼容

当前进度是按单词存：

```text
user_word_progress
  userId
  wordId
  correctCount
  wrongCount
  streakCorrect
  status
  nextReviewAt
```

这个可以继续保留。题型系统不改变 SRS 的主轴：

```text
掌握的是 word，不是某一道题
```

但是可以新增题型统计字段：

```js
practiceStats: {
  byType: {
    word_to_zh: {
      correct: 3,
      wrong: 1,
      lastPracticedAt: 1780000000000
    },
    spelling: {
      correct: 1,
      wrong: 2,
      lastPracticedAt: 1780000000000
    }
  }
}
```

短期可以不入库，只在本地或事件日志里记录。等题型多起来后，再决定是否写进云端。

推荐规则：

```text
第一阶段:
  SRS 仍按 known / unknown 更新，不区分题型

第二阶段:
  云端 submit 记录 questionType
  但 SRS 仍以 word 维度为主

第三阶段:
  如果整体 SRS 状态稳定，但 spelling 单项频繁错，可以提高 spelling 题出现概率
```

题型策略优先级：

```text
1. 如果单词整体是困难词，先降低难度，优先 word_to_zh
2. 如果单词整体稳定，但某个题型弱，再增加该题型
3. 不要在用户整体已经连续答错时继续强推 spelling
```

也就是说，“困难词降低难度”优先于“拼写弱项专项训练”。

## 9. 错题重试策略

错题重试要区分两种情况：

```text
same_question:
  同一道 question 延后再出一次，question.id 保持不变

easier_question:
  针对同一个 wordId 重新生成一道更简单的题，question.id 重新生成
```

推荐规则：

```text
word_to_zh 答错:
  same_question，延后 3 题重试

zh_to_word 答错:
  easier_question，退回 word_to_zh

spelling 答错:
  easier_question，下一次先出 zh_to_word 或 word_to_zh

relation_compare 答错:
  same_question 或 easier_question 都可以。第一版建议 easier_question，先回到普通识别题
```

SRS 更新时机：

```text
第一次答错就记录 unknown
重试题只影响后续 correct/wrong 统计，不撤销第一次错误
```

如果未来觉得这样惩罚太重，可以给重试成功增加补偿字段，但第一版不建议复杂化。

兼容规则：

```text
旧云函数不认识 questionType 也不影响

```

## 11. AI 生成题怎么接入

AI 生成题不要直接自由文本渲染，必须输出同样的 `question` 结构。

固定 prompt 让 AI 返回 JSON：

```text
你是英语词汇练习题生成器。
请基于给定单词、义项、词群关系和语料，生成一个 question JSON。
必须满足以下 schema：
{
  "type": "definition_to_word" | "relation_compare" | "sentence_blank",
  "wordId": "",
  "word": "",
  "senseId": "",
  "prompt": {},
  "choices": [],
  "answer": {},
  "meta": {
    "generator": "ai",
    "dataSource": "relation",
    "difficulty": 1-5
  }
}
只输出 JSON，不要输出解释。
```

AI 题进入系统前必须做校验：

```text
type 是否支持
wordId 是否存在
senseId 是否存在
prompt 是否符合该 type 的 schema
choices 是否有且只有一个 correct
choices[].value 是否等于 choices[].wordId
answer 是否和 correct choice 对得上
spelling 题 answer.acceptable 是否至少有一个值
英文题干是否过长
是否包含不适合小程序展示的内容
```

AI 题不应该直接进入长期数据源。建议先当作临时题：

```text
用户打开 AI拓展 -> 生成题 -> 当前 session 使用
```

如果质量稳定，再考虑缓存到：

```text
word_questions
```

## 12. 可选新增集合：word_questions

短期不需要建库。等 AI 题或人工题量变多，再新增：

```text
word_questions
```

结构：

```js
{
  _id: "question_word_purpose_definition_to_word_001",
  wordId: "word_purpose",
  senseId: "purpose_n_01",
  type: "definition_to_word",
  prompt: {},
  choices: [],
  answer: {},
  meta: {
    generator: "manual",
    dataSource: "definition",
    difficulty: 3,
    reviewIntent: "recognition"
  },
  status: "published",
  createdAt: 1780000000000,
  updatedAt: 1780000000000
}
```

适合缓存：

```text
高质量人工题
通过审核的 AI 题
语料挖空题
词群辨析题
```

不适合缓存：

```text
普通 word_to_zh / zh_to_word 选择题
```

这些本地规则生成就够了。

## 13. 分阶段落地

### 阶段一：本地多题型

目标：

```text
支持 word_to_zh / zh_to_word / spelling
```

改动：

```text
新增 question-builder.js
word-card 升级为 question-card
learn 页从 currentChoices 改为 currentQuestion
SRS 逻辑保持不变
```

### 阶段二：题型策略

目标：

```text
根据掌握程度动态调整题型
```

规则：

```text
新词先识别
熟一点再反向选择
再熟一点做拼写
困难词降低难度
复习词混合题型
```

### 阶段三：关系题和语料题

目标：

```text
接入 word_relations / content_lines
```

新增题型：

```text
relation_compare
sentence_blank
```

### 阶段四：AI 题

目标：

```text
AI拓展生成题也能复用 question schema
```

先 session 使用，质量稳定后再缓存到 `word_questions`。

## 14. 推荐结论

当前不建议直接在现有 `word-card` 上硬加拼写输入和新选项类型。

更稳的做法是：

```text
先抽象 question schema
再改 learn 页只认 currentQuestion
最后让不同题型共用同一套答题、SRS、音效、错题重试逻辑
```

第一版落地建议：

```text
word_to_zh
zh_to_word
spelling
```

暂时不建新集合。等关系题、语料题、AI 题质量稳定后，再考虑 `word_questions`。
