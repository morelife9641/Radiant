# 数据库与语料系统设计

本文档是当前项目后续接入微信云开发数据库的执行版设计。它合并了词书、单词、用户进度、用户偏好、Valorant / 美剧等主题语料系统，并回应 `项目设计与数据结构-review.md` 里的问题。

## 1. 设计结论

当前要按两套内容体系设计：

```text
词书系统
  -> words
  -> wordbooks
  -> wordbook_words

语料主题系统
  -> content_topics
  -> content_lines
  -> content_line_words
```

用户相关数据：

```text
users
user_word_progress
user_book_progress
```

MVP 第一批建议手动创建 9 个集合：

```text
users
words
wordbooks
wordbook_words
user_word_progress
user_book_progress
content_topics
content_lines
content_line_words
```

后续再加：

```text
study_sessions
study_events
sync_jobs
```

核心原则：

```text
单词只存一份。
词书只保存单词集合关系。
主题语料只保存真实句子、音频和出处。
用户进度按 userId + wordId 共享。
词书进度按 userId + bookId 聚合。
用户 preference 控制单词详情优先展示哪个主题的例句。
```

## 2. 产品关系图

```text
用户
  -> activeBookId: ielts
  -> preferredTopicIds: [valorant, friends]

词书 ielts
  -> wordbook_words
  -> words

主题 valorant
  -> content_lines
  -> content_line_words
  -> words

单词详情页 accurate
  -> 读取 words.word_accurate
  -> 读取用户 preferredTopicIds
  -> 查 content_line_words(word_accurate + preferred topic)
  -> 展示相关原句、角色、场景、音频
```

Valorant 既可以是一套主题语料，也可以是一本词书，但这两个身份必须分开：

```text
Valorant 主题语料 -> content_topics
Valorant 高频术语词书 -> wordbooks
```

不要把主题语料混进 `wordbooks`。

## 3. 当前必须创建的集合

### 3.1 users

用户基础信息、当前词书、偏好主题、设置。

```js
{
  _id: "openid_xxx",
  openid: "openid_xxx",
  accountId: "openid_xxx",
  nickname: "同学",
  avatarUrl: "",
  purpose: "exam",
  activeBookId: "ielts",
  preferredTopicIds: ["valorant"],
  settings: {
    dailyGoal: 10,
    accent: "us",
    autoPlayWordAudio: false,
    detailExampleMode: "preferred_first"
  },
  stats: {
    streakDays: 0,
    lastCheckInDate: "",
    totalLearned: 0
  },
  localMigration: {
    progressMigratedAt: null
  },
  createdAt: 1779700000000,
  updatedAt: 1779700000000
}
```

说明：

- `_id` 第一阶段可直接用微信 `openid`。
- `accountId` 先等于 `openid`，以后迁到 Supabase / 独立 App 时再映射成全平台用户 ID。
- `preferredTopicIds` MVP 直接放 `users`，不用单独建 `user_preferences`。
- 业务集合里的 `userId` 第一阶段也使用 `openid`，但 `users` 自身不再重复存 `userId`。

### 3.2 words

全局单词实体库，一个单词或短语只存一份。

```js
{
  _id: "word_accurate",
  word: "accurate",
  normalized: "accurate",
  type: "word",
  phonetic: {
    uk: "/ˈækjərət/",
    us: "/ˈækjərət/",
    default: "/ˈækjərət/"
  },
  audio: {
    us: "",
    uk: ""
  },
  audioPolicy: null,
  senses: [
    {
      pos: "a",
      translation: "正确无误的；精确的",
      definitionEn: "",
      definitionZh: "",
      collinsEn: "",
      collinsZh: "",
      synonyms: [],
      antonyms: [],
      gamingLink: null
    }
  ],
  contextStats: {
    totalLines: 0,
    byTopic: {}
  },
  createdAt: 1779700000000,
  updatedAt: 1779700000000
}
```

音频策略：

```text
优先使用 words.audio.us / words.audio.uk
如果为空，则按 audioPolicy 或前端默认规则拼接
```

当前小程序 `audio.js` 仍可按规则拼接。云端化后不要强制给每个词落完整 URL；只在例外、特殊文件名、私有签名 URL 场景写 `audio`。

`audioPolicy` 默认不写或为 `null`。它只用于覆盖默认拼接规则，例如某个词的音频不在默认 COS 桶、文件名特殊、或需要临时签名 URL。

`normalized` 规则：

```js
normalized(s) = s.trim().toLowerCase()
```

MVP 不去标点、不合并内部空格、不替换连字符。因此：

```text
easy-going !== easy going
favour !== favor
```

导入脚本和运行时必须共用同一套 normalize 逻辑，建议沉淀到 `utils/normalize.js` 或脚本侧同名函数。

语料分词规则必须和 `normalized` 对齐：

```text
tokenize(text):
  1. 按空白和常规句读切分
  2. 保留英文撇号和连字符
  3. 每个 token 再执行 normalized(token)
```

例如：

```text
We're -> we're
easy-going -> easy-going
plane, -> plane
```

不要在语料导入里把 `we're` 拆成 `we` / `re`，否则会和 `words.normalized` 不一致。

同形异义词策略：

```text
MVP 一词一记录。
lead / bank 这类同形异义词不拆多条 word。
不同义项放 senses[]。
```

这是有意限制，不是遗漏。等未来做“按义项学习”时，再引入 `word_senses` 或 sense-level progress。

CET4 v2 的复杂义项直接落在 `senses[]` 内。字段映射：

```text
collins_definition.en -> collinsEn
collins_definition.zh -> collinsZh
synonyms[].nuance_explanation -> synonyms[].nuanceEn
synonyms[].example_en -> synonyms[].exampleEn
synonyms[].example_zh -> synonyms[].exampleZh
antonyms -> antonyms
gaming_link -> gamingLink
```

IELTS 没有这些字段时保持空数组、空字符串或 `null`，前端按字段存在性渲染。

### 3.4 wordbook_words

词书和单词的关系表。它决定“某本词书包含哪些词、顺序如何、是否重点词”。

```js
{
  _id: "ielts_word_accurate",
  bookId: "ielts",
  wordId: "word_accurate",
  word: "accurate",
  normalized: "accurate",
  order: 123,
  chapter: "Word List 02",
  important: true,
  tags: ["ielts"],
  bookSenseOverride: null,
  createdAt: 1779700000000,
  updatedAt: 1779700000000
}
```

重要修正：

```text
_id 必须用 bookId + wordId。
不要用 bookId + order。
```

原因：`order` 未来可能重排，不能作为稳定主键。

`bookSenseOverride` 语义：

```text
如果为空，使用 words.senses。
如果非空，整段替换 words.senses。
不做逐字段 merge。
```

### 3.5 user_word_progress

用户对某个单词的全局掌握状态。跨词书共享。

```js
{
  _id: "openid_xxx_word_accurate",
  userId: "openid_xxx",
  wordId: "word_accurate",
  normalized: "accurate",
  status: "learning",
  easiness: 2.5,
  interval: 1440,
  nextReviewAt: 1779786400000,
  correctCount: 2,
  wrongCount: 1,
  lastResult: "known",
  lastBookId: "ielts",
  firstSeenAt: 1779700000000,
  lastReviewedAt: 1779700000000,
  updatedAt: 1779700000000
}
```

`status`：

```text
new
learning
reviewing
mastered
ignored
```

`lastBookId` 用途：

```text
只记录这个词最近一次是在哪本词书里被学习或复习。
不参与进度判断。
由 learn-submit 写入。
```

跨词书共享规则：

```text
用户在 IELTS 学过 accurate
  -> 更新 user_word_progress(openid, word_accurate)

用户切到 TOEFL
  -> TOEFL 也有 word_accurate
  -> 读取同一条 user_word_progress
  -> 继承学习状态
```

### 3.6 user_book_progress

用户对某本词书的聚合进度，用于首页和词书列表快速展示。

```js
{
  _id: "openid_xxx_ielts",
  userId: "openid_xxx",
  bookId: "ielts",
  learnedCount: 120,
  masteredCount: 36,
  totalWords: 3610,
  todayDone: 6,
  lastReviewedAt: 1779700000000,
  updatedAt: 1779700000000
}
```

重要规则：

```text
learnedCount 只统计“用户在本书内实际学过的词”。
用户在 IELTS 学过 accurate，不自动增加 TOEFL 的 learnedCount。
但 TOEFL 打开 accurate 时可以继承 user_word_progress。
```

为什么这样设计：

- 避免切换一本新词书后进度突然大幅增加，用户感知混乱。
- 保留“本书学习进度”和“全局单词掌握状态”的区别。

`dueCount` 不建议存这里：

```text
dueCount 随时间自然变化。
应查询 user_word_progress where nextReviewAt <= now 动态计算。
```

`todayDone` 读取和写入规则：

```text
读取时：
  如果 lastReviewedAt 不在今天，则 todayDone 视为 0。

写入时：
  如果 lastReviewedAt 不在今天，先把 todayDone 清零，再 +1。
  如果 lastReviewedAt 在今天，直接 +1。
```

### 3.8 content_lines

主题下的真实句子、台词、音频和出处。

Valorant 示例：

```js
{
  _id: "line_valorant_8f3a21c9",
  topicId: "valorant",
  text: "I am on a higher plane, chale, literally!",
  normalizedText: "i am on a higher plane chale literally",
  translationZh: "",
  audio: {
    fileName: "AstraPick.mp3",
    localPath: "audio/Astra/AstraPick.mp3",
    url: "https://static.wikia.nocookie.net/valorant/images/c/c7/AstraPick.mp3/revision/latest?cb=20210624210538"
  },
  speaker: {
    name: "Astra",
    type: "agent"
  },
  scene: {
    section: "Agent Selected/Unlocked",
    season: "",
    episode: "",
    timestampMs: null
  },
  source: {
    csvRow: 2,
    sourceFile: "valorant_quotes/lines.csv",
    sourceUrl: ""
  },
  wordCount: 9,
  createdAt: 1779700000000,
  updatedAt: 1779700000000
}
```

美剧示例：

```js
{
  _id: "line_friends_d41f8c2a",
  topicId: "friends",
  text: "We were on a break!",
  normalizedText: "we were on a break",
  translationZh: "我们当时分手了！",
  audio: {
    url: "https://..."
  },
  speaker: {
    name: "Ross",
    type: "character"
  },
  scene: {
    section: "",
    season: 3,
    episode: 15,
    timestampMs: 1234000
  }
}
```

`content_lines._id` 统一规则：

```text
line_${topicId}_${stableHash}

stableHash = md5(
  text + "|" +
  speaker.name + "|" +
  (audio.fileName || "") + "|" +
  (scene.section || "") + "|" +
  (scene.timestampMs || "")
).slice(0, 12)
```

不要按不同 topic 各自发明 `_id` 规则。导入脚本必须保证同一份源数据重复导入时得到相同 `_id`。

`stableHash` 的输入字段顺序固定，不直接 hash 整个 `scene` 对象，避免 Python / JS 对对象序列化顺序不一致导致重复导入产生不同 `_id`。

`translationZh` 可先为空。推荐后续用 AI 批量翻译后入库并人工抽检，不建议每次打开详情页实时翻译。

### 3.9 content_line_words

台词和单词的匹配关系。单词详情页靠它快速查例句。

```js
{
  _id: "line_valorant_8f3a21c9_word_plane",
  topicId: "valorant",
  lineId: "line_valorant_8f3a21c9",
  wordId: "word_plane",
  normalized: "plane",
  surface: "plane",
  positions: [
    {
      start: 17,
      end: 22
    }
  ],
  matchType: "exact",
  createdAt: 1779700000000
}
```

`_id` 使用：

```text
lineId + wordId
```

同一个词在同一句里出现多次时，不创建多行，统一合并到 `positions[]`。例如 `"the the the"` 只写一条 `lineId + word_the`，`positions` 里放 3 个位置。

`matchType`：

```text
exact      原词命中
lemma      词形还原命中
phrase     短语命中
manual     人工标注
```

MVP 可以先只做 `exact`。

## 4. 单词详情页如何使用 preference

用户设置：

```js
users.preferredTopicIds = ["valorant"]
```

打开单词详情：

```text
1. 当前单词 normalized -> wordId
2. 读取 users.preferredTopicIds
3. 调用 topic-fetch.wordExamples
4. 云函数按 preferredTopicIds 逐个 topic 查询 content_line_words:
   topicId = 单个 topicId
   wordId = 当前 wordId
5. 根据 lineId 查 content_lines
6. 展示 text / speaker / scene / audio
```

不要在前端直接使用 `topicId in preferredTopicIds AND wordId = X` 查询。微信云数据库里 `in` 和复合索引的表现不可控，云函数应按 topic 逐个查再合并排序。

展示顺序：

```text
preferred topic 命中
  -> 优先展示 3 条

preferred topic 没命中
  -> 展示其他 topic 命中

全部没命中
  -> 不显示语料区，或显示普通例句
```

同一 topic 内排序：

```text
1. audio.url 存在优先
2. speaker 尽量多样
3. lineId 稳定排序
```

`topic-fetch.wordExamples` 返回结构：

```js
{
  ok: true,
  primary: [
    {
      line: {},
      words: []
    }
  ],
  secondary: [],
  topics: [
    {
      id: "valorant",
      name: "Valorant",
      cover: {}
    }
  ]
}
```

不建议每次打开详情都全文搜索 `content_lines.text`。应提前生成 `content_line_words`。


### 6.3 learn-submit

职责：

```text
生成今日学习词
提交答题结果
云端计算 SRS
更新 user_word_progress
更新 user_book_progress
处理本地 progress bulkImport
```

提交输入：

```js
{
  action: "submit",
  bookId: "ielts",
  wordId: "word_accurate",
  result: "known"
}
```

批量导入输入：

```js
{
  action: "bulkImport",
  items: [
    {
      bookId: "ielts",
      word: "accurate",
      progress: {
        easiness: 2.5,
        interval: 1440,
        nextReviewAt: 1779786400000,
        correctCount: 2,
        wrongCount: 1,
        status: "learning",
        firstSeenAt: 1779700000000,
        lastReviewedAt: 1779700000000,
        updatedAt: 1779700000000
      }
    }
  ]
}
```

批量导入输出：

```js
{
  ok: true,
  importedCount: 120,
  skippedWords: ["roll film", "in addition to"],
  failedItems: []
}
```

找不到 `wordId` 的词跳过并写入 `skippedWords`，不让整个导入失败。

当前实现：

```text
stub
```

## 8. 权限规则

建议第一阶段所有写操作都走云函数。

微信云数据库集合权限不是任意 RBAC，控制台常见是几种预设权限。实际落地建议：

```text
用户私有集合：
  选择“仅创建者可读写”或“仅管理端可写，客户端只读本人数据”
  所有写操作通过云函数完成

公共只读集合：
  选择“所有用户可读，仅管理端可写”
  导入脚本 / 管理后台 / 云函数负责写入
```

```text
users
  本人可读，云函数写

words
  所有用户可读，仅管理员 / 云函数可写

wordbooks
  所有用户可读，仅管理员 / 云函数可写

  所有用户可读，仅管理员 / 云函数可写

  本人可读，仅云函数可写
```

### 9.1 本地 progress 首次迁移

首次登录云端后：


```text

仍然缺失 -> 优先保留云端。
```

不要用“easiness 较高者”做合并，容易虚高掌握度。

### 9.2 today key 和时区

当前代码用：

```js
new Date().toDateString()
```

建议改成统一工具：

```text
getDateKeyAsiaShanghai() -> YYYY-MM-DD
```

所有日期 key 和打卡统计统一按东八区。

小程序侧最小实现：

```js
function getDateKeyAsiaShanghai() {
  const shanghai = new Date(Date.now() + 8 * 60 * 60 * 1000);
  return shanghai.toISOString().slice(0, 10);
}
```

放到 `miniprogram/utils/date.js`，导入脚本侧也使用同样规则。

## 12. 更新、搜索与回滚

### 12.1 词书更新

词书修订流程：

```text
导入新版词书
  -> 与现有 words / wordbook_words diff
  -> 新词 insert
  -> 修订释义 update words 或 bookSenseOverride
  -> 删除词标记 archived，不物理删除
  -> wordbooks.contentVersion + 1
```

字段语义：

```text
schemaVersion:
  数据结构版本。schema 变化才升级，用于数据迁移。

contentVersion:
  内容修订版本。词条增删改、释义更新时升级，用于客户端缓存失效。
```

客户端启动时比对 `wordbooks.contentVersion`，版本变化后失效本地词书缓存。

如果 `bookSenseOverride` 从有值改为 `null`，导入脚本必须显式把 `wordbook_words.bookSenseOverride` 设为 `null`，不能因为新版数据缺字段就忽略旧值。

### 12.2 搜索

搜索建议走云函数，不让页面直接查数据库。

```text
全局搜：
  words.normalized 前缀匹配

本书内搜：
  wordbook_words.normalized 前缀匹配 + bookId

主题台词搜：
  content_lines.normalizedText 前缀 / 包含匹配 + topicId
```

MVP 先做全局搜词即可。

### 12.3 灰度与回滚

从本地 storage 切到云端时必须留开关：

```text
wordbookDataSource = local | cloud
progressDataSource = local | cloud
topicDataSource = cloud
```

这些开关存到 `app_config` 集合：

```js
{
  _id: "default",
  wordbookDataSource: "local",
  progressDataSource: "local",
  topicDataSource: "cloud",
  updatedAt: 1779700000000
}
```

小程序启动时拉一次并缓存。出问题时改云端 `app_config` 即可回滚。

先在测试环境导入并跑通，再切生产。云函数保留旧路径至少 2 周，确认稳定后再删除。
