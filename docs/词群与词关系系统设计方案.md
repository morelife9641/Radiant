# 词群与词关系系统设计方案

本文档用于说明后续怎么处理单词详情里的同义词、近义词、反义词、易混淆词和词群关系。

核心目标是：一个单词只存一份基础信息，单词之间的关系单独存。这样 `purpose / aim / goal / intention / objective` 这种词群可以被多个单词详情页复用，而不是在每个单词里重复写一份。

## 1. 为什么需要词群关系

当前 `words` 集合适合存一个单词自身的信息：

```js
{
  _id: "word_purpose",
  word: "purpose",
  phonetic: {},
  senses: [
    {
      pos: "n",
      senseId: "purpose_n_01",
      translation: "目的；意图；用途",
      synonyms: [],
      antonyms: [],
      confusing: []
    }
  ]
}
```

这种结构做 MVP 很快，但它有一个问题：同义词、反义词、易混淆词本质上不是一个单词自己的属性，而是多个词之间的关系。

比如：

```text
purpose / aim / goal / intention / objective
```

如果只把这组数据写进 `purpose` 的 `senses[].synonyms`，那进入 `aim` 的详情页时，还要再写一遍 `purpose / goal / intention / objective`。后面词量一多，重复数据会越来越多，也很难维护。

所以推荐把词群关系拆出来：

```text
words
  存单词自己的基础信息

word_relations
  存两个词之间的关系，比如 purpose -> goal 是 near_synonym

word_relation_groups
  存一组词共同的解释，比如 purpose / aim / goal / intention / objective 这一组怎么区分
```

## 2. 设计原则

1. `words` 仍然是全局单词实体，不跟词书绑定。
2. `wordbook_words` 只表示某个单词属于某本词书，以及它在词书里的顺序。
3. `content_lines / content_line_words` 继续表示真实语料和命中的单词。
4. 同义词、反义词、易混淆词不要长期重复塞进每个 `words` 文档里。
5. 词群关系应该支持从任意一个词进入详情页时都能展示。
6. `words.senses[]` 需要有稳定 `senseId`，关系数据引用义项时引用 `senseId`，不要引用释义文本。
7. `word_relations` 的双向数据可以冗余存储，但必须由导入脚本自动生成，不允许人工维护两边。

## 3. 推荐新增集合

### 3.1 word_relation_groups

这个集合表示一个词群，负责存“这一组词整体怎么理解”。

```js
{
  _id: "group_purpose_aim_goal_intention_objective",
  type: "synonym_set",
  title: "purpose / aim / goal / intention / objective",
  memberWordIds: [
    "word_purpose",
    "word_aim",
    "word_goal",
    "word_intention",
    "word_objective"
  ],
  members: [
    {
      wordId: "word_purpose",
      word: "purpose",
      role: "general",
      shortZh: "目的；用途"
    },
    {
      wordId: "word_aim",
      word: "aim",
      role: "target",
      shortZh: "目标；瞄准点"
    },
    {
      wordId: "word_goal",
      word: "goal",
      role: "result",
      shortZh: "目标；结果"
    }
  ],
  summaryEn: "These words all describe something someone wants to achieve, but they differ in focus.",
  summaryZh: "这组词都和“想达到的目标”有关，但侧重点不同。",
  dimensions: [
    {
      key: "focus",
      nameZh: "侧重点",
      items: [
        {
          wordId: "word_purpose",
          textZh: "为什么做这件事"
        },
        {
          wordId: "word_aim",
          textZh: "想对准或努力达到的目标"
        },
        {
          wordId: "word_goal",
          textZh: "具体想完成的结果"
        },
        {
          wordId: "word_intention",
          textZh: "内心打算"
        },
        {
          wordId: "word_objective",
          textZh: "正式、可衡量的目标"
        }
      ]
    }
  ],
  examples: [
    {
      en: "Her purpose was to help children learn.",
      zh: "她的目的是帮助孩子学习。"
    }
  ],
  source: {
    type: "manual_ai_reviewed",
    note: "人工确认后的 AI 辅助生成"
  },
  status: "published",
  createdAt: 1780000000000,
  updatedAt: 1780000000000
}
```

字段说明：

```text
type:
  synonym_set      同义 / 近义词群
  confusing_set    易混淆词群
  antonym_axis     反义词轴
  mixed            综合词群

memberWordIds:
  冗余字段，方便快速判断和必要时建索引。以 members[].wordId 为准，由导入脚本生成

members:
  权威成员列表，方便前端直接渲染词群成员

dimensions:
  用来表达词之间的差异维度，比如正式程度、语气强弱、具体程度、使用场景。内部使用 items[] + wordId，不用词名做 key
```

### 3.2 word_relations

这个集合表示两个词之间的关系，负责支持“从当前词查相关词”。

```js
{
  _id: "rel_word_purpose_purpose_n_01_word_goal_goal_n_01_near_synonym",
  fromWordId: "word_purpose",
  fromWord: "purpose",
  toWordId: "word_goal",
  toWord: "goal",
  relationType: "near_synonym",
  groupId: "group_purpose_aim_goal_intention_objective",
  direction: "bidirectional",
  strength: 4,
  senseScope: {
    pos: "n",
    fromSenseId: "purpose_n_01",
    toSenseId: "goal_n_01"
  },
  explanationEn: "A purpose is the reason for doing something; a goal is the result you want to reach.",
  explanationZh: "purpose 更偏“为什么做”，goal 更偏“想达成的具体结果”。",
  exampleEn: "The purpose of the project is education, and its goal is to reach 10,000 students.",
  exampleZh: "这个项目的目的是教育，目标是覆盖一万名学生。",
  tags: ["abstract", "exam", "common"],
  status: "published",
  createdAt: 1780000000000,
  updatedAt: 1780000000000
}
```

字段说明：

```text
relationType:
  synonym        基本同义
  near_synonym   近义但有区别
  confusing      易混淆
  antonym        反义
  contrast       对比关系
  related        相关词

fromWordId / toWordId:
  支持从当前单词详情页快速查询

groupId:
  关联到词群说明

strength:
  关系强度，1-5。前端可以优先展示强关系

senseScope:
  说明这条关系只适用于哪个词性或哪个义项。必须优先使用 fromSenseId / toSenseId，不用释义文本当标识

status:
  draft        草稿，导入后暂不展示
  published    已发布，前端可展示
  hidden       临时隐藏，保留数据但前端不展示
  deprecated   已废弃，保留迁移痕迹或历史追溯
```

`word_relations._id` 生成规则必须包含 `senseScope`，避免同一对词在不同义项下出现同类关系时撞车。

推荐格式：

```text
rel_{fromWordId}_{fromSenseId}_{toWordId}_{toSenseId}_{relationType}
```

示例：

```text
rel_word_purpose_purpose_n_01_word_goal_goal_n_01_near_synonym
```

如果某条关系不限定具体义项，`fromSenseId / toSenseId` 可以用 `any` 占位：

```text
rel_word_good_any_word_bad_any_antonym
```

最终唯一性仍由导入脚本按以下组合校验：

```text
fromWordId + toWordId + relationType + senseScope
```

## 4. 存储策略：双向冗余，但由脚本生成

同义、近义、反义、易混淆关系都可能需要从任意一个词进入详情页时快速查到。小程序端更适合简单查询，所以推荐：

```text
数据库里保存双向 relation
人工或 AI 只维护一份源数据
导入脚本自动生成镜像关系
```

也就是说，人工整理时可以只写：

```json
{
  "fromWordId": "word_purpose",
  "toWordId": "word_goal",
  "relationType": "near_synonym",
  "direction": "bidirectional",
  "explanationZh": "purpose 更偏“为什么做”，goal 更偏“想达成的具体结果”。"
}
```

导入脚本自动生成：

```text
word_purpose -> word_goal
word_goal -> word_purpose
```

镜像规则：

```text
direction = bidirectional:
  自动生成 from/to 对调的镜像 relation

direction = directional:
  只生成原始方向

relationType = antonym:
  默认也可以双向，但 explanationZh 可以由脚本或人工提供反向版本

relationType = related:
  如果只是松散相关，允许 directional
```

这样做的理由：

```text
优点:
  详情页只查 fromWordId，简单稳定
  不需要 OR 查询 fromWordId / toWordId
  小程序端分页、排序、缓存都更容易做

代价:
  数据量会变多
  必须有导入脚本和校验脚本兜底
```

对当前规模来说，关系数据量可以接受。一个 10 词词群最多生成 90 条 relation，但 IELTS 词书第一阶段不会每个词都生成 10 词大组，云数据库和小程序查询压力都可控。

## 5. 为什么要同时有 group 和 relation

只存 `word_relation_groups` 的问题是：进入 `purpose` 页面时，要查所有包含 `purpose` 的 group，再从 group 里找成员，查询和排序都比较麻烦。

只存 `word_relations` 的问题是：可以查到 `purpose -> goal`，但缺少整组词的共同解释和对比维度。

所以推荐两个都保留：

```text
word_relation_groups
  管整组词怎么讲清楚

word_relations
  管当前词详情页怎么快速查出来
```

前端进入 `purpose` 详情页时：

```text
1. 查 word_relations where fromWordId = "word_purpose"
2. 按 relationType 分到 近义词 / 反义词 / 易混淆 tab
3. 如果 relation 里有 groupId，再批量查 word_relation_groups
4. 展示时高亮当前词 purpose
```

前端进入 `aim` 详情页时：

```text
1. 查 word_relations where fromWordId = "word_aim"
2. 同样能查到 purpose / goal / intention / objective
3. 复用同一个 group 的整体解释
```

一致性规则：

```text
如果 relation.groupId 非空:
  fromWordId 必须在 group.members[].wordId 中
  toWordId 必须在 group.members[].wordId 中

如果 group.memberWordIds 存在:
  必须等于 members[].wordId 的去重结果

如果 relation.senseScope.fromSenseId 非空:
  必须能在 words[fromWordId].senses[].senseId 中找到

如果 relation.senseScope.toSenseId 非空:
  必须能在 words[toWordId].senses[].senseId 中找到
```

这些规则由导入脚本校验。前端和云函数默认相信导入后的数据已经干净。

## 6. 和现有系统的关系

当前已有结构不需要推倒重来。

```text
words
  单词基础资料，比如音标、释义、音频、词性、义项

wordbooks
  词书元信息，比如 IELTS 核心词

wordbook_words
  词书和单词的关系，比如 IELTS 第 128 个词是 purpose

content_topics
  语料主题，比如 tbbt、ted

content_lines
  真实语料句子和音频片段

content_line_words
  某句话命中了哪些单词

word_relation_groups
  新增：词群整体解释

word_relations
  新增：两个词之间的关系
```

一个单词详情页的数据来源可以变成：

```text
基础 tab:
  words

语料 tab:
  content_line_words -> content_lines -> content_topics

近义词 tab:
  word_relations where fromWordId = 当前 wordId and relationType in ["synonym", "near_synonym"]

反义词 tab:
  word_relations where fromWordId = 当前 wordId and relationType = "antonym"

易混淆 tab:
  word_relations where fromWordId = 当前 wordId and relationType in ["confusing", "contrast"]

AI拓展 tab:
  可以基于 words + relations + corpus 做动态生成或缓存
```

## 8. 导入文件约定

为了和当前云数据库导入习惯一致，后续导入文件建议：

```text
word_relation_groups.import.json
word_relations.import.json
```

注意：文件后缀虽然是 `.json`，但内容使用 JSONL 格式，也就是一行一个 JSON 对象。

另外建议保留一个“源数据文件”，用于人工维护：

```text
word_relation_sources.import.json
```

源数据可以只写单向，导入工具输出真正进库的 `word_relations.import.json`。

示例：

```json
{"_id":"group_purpose_aim_goal_intention_objective","type":"synonym_set","title":"purpose / aim / goal / intention / objective"}
{"_id":"group_large_big_huge_enormous","type":"synonym_set","title":"large / big / huge / enormous"}
```

不要导入普通数组格式：

```json
[
  {"_id":"group_a"},
  {"_id":"group_b"}
]
```

云数据库导入时更适合 JSONL。

## 9. 导入脚本职责

导入脚本需要做四件事：

```text
1. 读取 word_relation_sources.import.json
2. 校验 wordId / senseId / groupId 是否存在
3. 根据 direction 自动生成镜像 relation
4. 输出 word_relations.import.json 和 word_relation_groups.import.json
```

必须校验：

```text
relation 的 fromWordId / toWordId 必须存在于 words
relation 的 fromSenseId / toSenseId 必须存在于对应 word.senses[]
relation.groupId 非空时，fromWordId / toWordId 必须都在 group.members[] 里
group.memberWordIds 必须由 members[].wordId 自动生成
同一个 fromWordId + toWordId + relationType + senseScope 不能重复
生成后的 relation._id 必须包含 fromSenseId / toSenseId；无具体义项时用 any 占位
```

不建议人工直接编辑最终的 `word_relations.import.json`。最终文件应该是脚本产物。

## 10. 索引建议

`word_relations` 建议索引：

```text
idx_from_type_strength
  fromWordId 升序
  relationType 升序
  strength 降序

idx_group
  groupId 升序
```

如果未来决定改成单向存储，并在查询时做 `fromWordId / toWordId` 双字段 OR 查询，再补：

```text
idx_to
  toWordId 升序
```

当前推荐双向冗余存储，详情页主要查 `fromWordId`，所以 `idx_to` 暂不作为必建索引。

`word_relation_groups` 建议索引：

```text
idx_type_status
  type 升序
  status 升序
```

查询详情页时主要走 `word_relations.fromWordId`，不要依赖在 `word_relation_groups.memberWordIds` 数组里硬查。

## 11. 分阶段落地

### 阶段一：MVP

继续允许 `words.senses[]` 里放少量 `synonyms / antonyms / confusing`，用于快速验证详情页 UI。

阶段一内联结构也必须使用对象数组，不允许只写字符串数组。

推荐结构：

```js
{
  senseId: "purpose_n_01",
  pos: "n",
  translation: "目的；意图；用途",
  synonyms: [
    {
      wordId: "word_goal",
      word: "goal",
      relationType: "near_synonym",
      strength: 4,
      noteZh: "goal 更偏想达成的具体结果"
    }
  ],
  antonyms: [
    {
      wordId: "word_aimlessness",
      word: "aimlessness",
      relationType: "antonym",
      strength: 3,
      noteZh: "aimlessness 表示没有明确目标"
    }
  ],
  confusing: [
    {
      wordId: "word_function",
      word: "function",
      relationType: "confusing",
      strength: 4,
      noteZh: "function 更偏功能，purpose 更偏目的"
    }
  ]
}
```

这样阶段二迁移时可以直接把 `wordId / relationType / strength / noteZh` 转成 `word_relation_sources`，不需要再根据字符串反查实体。

适合：

```text
先做 1-10 个高频单词示例
先验证页面展示
先验证用户是否喜欢这种学习方式
```

### 阶段二：关系集合

新增 `word_relations`，详情页的近义词、反义词、易混淆 tab 改成查这个集合。

迁移规则：

```text
阶段二开始后:
  word_relations 是权威数据源
  words.senses[].synonyms / antonyms / confusing 只作为旧数据 fallback

阶段二稳定后:
  批量把 words.senses[] 里的关系迁移到 word_relation_sources
  再由脚本生成 word_relations
  前端取消 fallback，只查 word_relations
```

不建议长期做 union 查询。短期 fallback 可以降低迁移风险，但长期会让数据来源变模糊。

适合：

```text
开始批量加工 IELTS 词书
需要从 aim 页面也能看到 purpose
需要让关系数据复用
```

### 阶段三：词群集合

新增 `word_relation_groups`，用于展示整组词的对比、维度、例句和总结。

适合：

```text
做更像“词群学习”的页面
做 AI 拓展
做一组词的横向比较
```

### 阶段四：缓存摘要

如果详情页性能压力变大，可以在 `words` 里保留轻量摘要字段。

例如：

```js
{
  relationSummary: {
    synonymsCount: 8,
    antonymsCount: 3,
    confusingCount: 4,
    updatedAt: 1780000000000
  }
}
```

但这个字段只做展示提示，不作为权威数据源。

`relationSummary` 由导入脚本在生成 `word_relations` 后顺手回填，不由小程序运行时聚合计算。这样可以避免详情页触发额外 count 查询。

## 12. 暂不实现但预留的扩展

### 12.1 词群之间的关系

有些关系不是词和词之间，而是词群和词群之间。

例如：

```text
happy / glad / pleased
sad / unhappy / depressed
```

这两组之间可以形成反义群对照。短期可以先用 `word_relations` 表达单词级反义；如果后续需要做“词群对词群”的学习页面，再新增：

```text
word_group_relations
```

可能结构：

```js
{
  _id: "group_rel_happy_sad_antonym",
  fromGroupId: "group_happy_glad_pleased",
  toGroupId: "group_sad_unhappy_depressed",
  relationType: "antonym_axis",
  explanationZh: "一组表达积极情绪，一组表达消极情绪。"
}
```

这个集合不作为当前阶段必做项，只保留设计空间。

换句话说，当前阶段并不是不能表达跨词群反义。`happy -> sad`、`pleased -> depressed` 这种单词级反义仍然用 `word_relations.relationType = "antonym"`。`word_group_relations` 的价值是做“整组词对整组词”的学习页，而不是替代单词级反义。

## 13. 推荐结论

短期可以继续把少量数据放在 `words.senses[]`，因为开发快，适合做样例。

长期建议新增：

```text
word_relations
word_relation_groups
```

这样同义词、反义词、易混淆词都能复用，进入任意一个词的详情页都能看到同一组关系，不需要在每个单词里重复维护一遍。

最终推荐的数据职责是：

```text
words:
  这个词是什么

word_relations:
  这个词和另一个词是什么关系

word_relation_groups:
  这一组词放在一起怎么讲清楚

content_lines:
  这些词在真实语料里怎么出现
```

落地优先级：

```text
第一优先级:
  给 words.senses[] 增加 senseId
  确定阶段一 senses[].synonyms / antonyms / confusing 使用对象数组
  确定 word_relations 双向冗余由脚本生成
  dimensions 改成 items[] + wordId

第二优先级:
  新增 word_relations
  写导入校验和镜像生成脚本
  详情页从 relations 查询

第三优先级:
  新增 word_relation_groups
  做词群整体解释和对比 UI
```
